Focus Queue context redesign

FOC-036 · Analysis of task, project, and agent context · 20 October 2026 · Measured against main at a762ed0 and 106 live task contexts

Bottom line. A freshly launched Focus Queue agent reads about 26.6 KB (≈6.7K tokens) of fixed context before it does anything. FOC-036 reached 44.8 KB. The user's actual request can be as little as 1% of that. For FOC-035 the request was 286 bytes. The launch prompt repeated it twice inside a 4.9 KB procedural template. A 12.9 KB global CLAUDE.md and five must-read files surrounded it.

The fix is structural, not editorial. Give every fact exactly one owner layer. Let the host (launcher, CLI, hooks) do what the prompt currently asks the agent to do. Load procedure on demand instead of on every launch. A realistic target is ≈9 KB total and a ≈0.7 KB launch brief, about a two-thirds reduction. Fix this base layer before the learned data.md layer grows, because learned facts on top of a bloated base compound the problem.

Corpus findings across 106 task contexts

  • 45 subtasks store assignmentDescription equal to (or a prefix of) initialPrompt, so the launch prompt shows the request twice.
  • Long prompts appear 2–6 times inside one context.json: initialPrompt, assignmentDescription, summary, and archive snapshots. The largest context.json is 305 KB.
  • 48/106 tasks carry the generic success criterion “Confirm the requested behavior and record verification results.” It costs bytes in every prompt and tells the agent nothing.
  • 9/106 plans carry the filler “Why: This task advances the recorded project goal.”. Generated BLUFs paste the raw prompt as “Current focus”: FOC-035's BLUF contains the 286-byte request with its typos.
  • The rendered template repeats the support-directory path 14 times, the agent UUID 11 times, and the ticket ID 15 times. The launcher already exports all three as environment variables.

Admission test: where does a sentence belong?

  1. Can the host do it instead? Then it is code, not context: registration, worktree creation, default IDs, plan creation, label management.
  2. Is it true for every session the user runs? Then it belongs in the user layer.
  3. Is it true only inside a Focus Queue pane? Then it belongs in the runtime layer, loaded only when FOCUS_QUEUE_TASK_ID is set.
  4. Is it about this codebase for any agent? Then AGENTS.md. If it is about this project's goals and conventions, project.md. If it is about this objective, the task plan.
  5. Was it learned rather than designed? Then the matching data.md, never a template.
  6. Is it already said by a higher layer? Then delete it.

7. Learned-data layer, after the base is clean

  • Three scopes, one shape. user/data.md, projects/<p>/data.md, and tasks/<ID>/data.md. Each holds dated, sourced bullets under a byte cap (user 2 KB, project 3 KB, task 2 KB).
  • Write path. A focus-queue-session remember "<fact>" [--scope task|project|user] verb, as FOC-010's summary already proposes. Without --scope, a small model applies FOC-014's admission rules. Deterministic checks enforce identity and the cap.
  • Read path. The capsule lists the paths. The brief says “Read first: task plan and task data”, and project data.md is read with project.md. User data lives in the global layer, so it is already loaded.
  • Hygiene. When a scope exceeds its cap, a compaction pass merges duplicates and retires superseded facts into agent-log.md. Learned facts never get copied into templates.

Risks

  • Agents skip lifecycle calls once instructions get shorter. Mitigate with host-side registration, a Stop hook that reports idle, and a dashboard measure of the attach/complete rate before and after Phase 1.
  • Provider differences. Kimi takes the prompt non-interactively via --prompt, and Codex has no --append-system-prompt. The brief must work as plain prompt text for both.
  • Old branches. The contract-refresh and routing branches are 56 commits behind. Port the ideas; do not merge them blindly.

9. Decisions for you

  1. Approve Phase 1 as the next task? It is self-contained, inside FocusQueueCore, test-covered, and removes most of the visible repetition.
  2. Where should the Focus Queue runtime rules live for Claude: --append-system-prompt (invisible, deterministic) or the visible brief (portable across providers)? Recommendation: the visible brief for all providers first, then the system prompt for Claude.
  3. Keep the Output Contract's worked example in global CLAUDE.md? It is the largest optional block (~1.5 KB), but it is your style guide, so this is your call.
  4. Merge plan.md and practices.md into one project.md? This changes the project-document set that hydration creates.
